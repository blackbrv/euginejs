The same `EugineDocument` feeds both renderers, but they take **incompatible** component-renderer
shapes — so you build a separate `ComponentRegistry<T>` per context.

The diagram below emphasizes that these are two separate registries fed from the same document,
not one registry serving two outputs.

## Server

`@euginejs/renderer-server` excludes the `DOM` lib from its TypeScript config entirely, so importing
any `window`/`document` API there is a compile error rather than a runtime surprise in production.

## Browser

<CodeFromFile file="rendering" region="dom" title="Rendering to the DOM" />

`update()` walks the tree and reuses a node's cached element when `previous === node`, recursing
into children regardless — a changed descendant patches itself into the live DOM without forcing
its ancestors to rebuild. Elements for ids no longer visited are garbage-collected.

## Selection

`setSelection()` toggles the `data-eugine-selected` attribute on live elements with no rebuild and
no reconcile, so element identity, scroll position, and focus all survive:

```ts
editor.selection.onSelectionChange(({ ids }) => renderer.setSelection(ids));
```

Eugine ships no selection styling. Target the attribute yourself:

```css
[data-eugine-selected] { outline: 2px solid #6366f1; }
```

## Missing components

`onMissingComponent` controls what happens when a node's type is not registered: `"placeholder"`
(the default), `"omit"`, or `"throw"`. Both renderers resolve types strictly through the registry
and never dynamically import anything named inside document data.
