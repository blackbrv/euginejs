`History` is a transaction-aware undo/redo stack over commands — in-session and ephemeral, cleared
on `editor.load()`. For durable checkpoints that survive a refresh or a deploy ("Draft v3",
"Published v2", with rollback), see [Versioning](/docs/guides/versioning) instead — a separate
concept, and a separate package.

```ts
editor.history.undo();
editor.history.redo();
editor.history.canUndo();
editor.history.canRedo();
editor.history.clear();
```

## Replay is atomic

If any command throws part-way through an undo, the document is restored to exactly where it
started and **both stacks are left untouched**. The transaction is popped only after the replay
succeeds.

The failure this prevents is subtle and severe: pop-then-replay leaves the document half-reverted
*and* drops the transaction from both stacks, putting the user's edit permanently out of reach of
undo and redo alike. A failed replay raises `EUGINE_HISTORY_ERROR` with the original error as its
`cause`.

## Undo is scoped to the client

With a `clientId`, `undo()` and `redo()` skip transactions authored elsewhere, so Ctrl+Z never
reverts the edit a colleague just made. `canUndo()` reflects the same scoping, so a toolbar button
greys out honestly.

```ts
const editor = createEditor({ clientId: "user-42" });
```

<Callout type="warn">
  This is per-client scoping, not operational transformation. Undoing past a later remote edit
  replays each command's inverse against the *current* document — safe, in that it will not clobber
  a concurrent edit or throw, but it does not transform intent the way a CRDT or OT layer would.
</Callout>
